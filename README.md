srvpru is a duel server for [ygopro](https://github.com/mycard/ygopro). It provides matchmaking and various
other features; on top of that, it offers a web UI for administration.

srvpru stays compatible with [srvpro](https://github.com/mycard/srvpro) in the vast majority of cases.

## Features

- **Built-in web portal** — the admin UI (room list, players, live scores, plugin switches, accounts and
  configuration) is served by the same process on the same host. No PHP, no second deployment, no
  configuration file to keep in sync with the server.
- **Live room list** — pushed over WebSocket, so rooms appear, update and disappear in the browser as they are
  created, played and destroyed. No polling.
- **Hot-swappable plugins** — plugins register themselves at link time, and can be enabled, disabled and
  reconfigured at runtime from the portal or the HTTP API, without restarting the server. Plugin dependencies
  are resolved automatically.
- **Two duel backends** — each room runs either the embedded ygopru `DuelHost` in-process or a spawned external
  `ygopro` binary, selectable per room.
- **Accounts and permissions** — JWT login backed by SQLite, with per-permission authorization.
- **Configuration without editing files** — files, `SRVPRO_*` environment variables and the database are merged
  into one configuration; changes made in the portal apply immediately and survive a restart.
- **The srvpro protocol, not a subset of it** — room names, mode options, join/leave/reconnect flows and the
  whole STOC/CTOS message set behave the way srvpro players expect.

## Requirements

The engine reads its data relative to the working directory:

- `cards.cdb` — the card database, take one from
  [ygopro-database](https://github.com/mycard/ygopro-database); `expansions/*.cdb` are read as well
- `script/` — the Lua card scripts, take them from
  [ygopro-scripts](https://github.com/Fluorohydride/ygopro-scripts)
- `lflist.conf` (optional; `expansions/lflist.conf` is tried first)

These paths come from the engine's own configuration and can be overridden with `system.conf` or `YGOPRO_*`
environment variables.

Building needs a Rust toolchain (edition 2024), a C++14 compiler for ocgcore, and Node 22 for the portal.

## Building

```bash
cargo build --release -p srvpro-app

cd srvpro-portal
npm ci
npm run build # → srvpro-portal/dist
```

`srvpro-app` enables `api`, `zip` and `card` by default. Building it with
`--no-default-features --features zip,card` produces a headless server without the HTTP API and the portal.

## Running

A prebuilt image is published on Docker Hub as `iami/srvpru`. Fetch the data next to it first:

```bash
git clone --depth 1 https://github.com/mycard/ygopro-database
git clone --depth 1 https://github.com/Fluorohydride/ygopro-scripts script
touch srvpro.db # docker would otherwise turn the mount point into a directory

# pull the image and run it
docker run -d --name srvpru -p 7911:7911 -p 7922:7922 \
    -v "$PWD/ygopro-database/locales/zh-CN/cards.cdb:/srvpro/cards.cdb" \
    -v "$PWD/script:/srvpro/script" \
    -v "$PWD/srvpro.db:/srvpro/srvpro.db" \
    iami/srvpru
```

`locales/zh-CN` is any other language directory of ygopro-database.

## Setup 

On the first start srvpru creates the account database (`api_database`, default `srvpro.db`), its schema, a
token signing secret, and an `admin` account. If `bootstrap_password` is not set, a random password is
generated and written to the log:

```text
no initial password is configured, created the account admin in srvpro.db with the generated password <...>
```

Log in with it at `http://<host>:7922/` and change it there.

## Usage

The usage is almost entirely the same as the [233 server's](https://ygo233.com/usage): the room name codes
still apply, so `M#xxxx` gives a match room and `T#xxxx` a tag room.

The codes it adds on top of that:

| Code | Meaning |
| ---- | ------- |
| `BO<n>` | best of n |
| `NM` / `NOMASK` | do not mask the opponent's unknown cards |
| `E<n>` / `ENGINE<n>` | duel backend: `1` embedded, `2` the external `./ygopro` binary |
| `G` / `GENESYS` | the Genesys ban list |

For example, `T,BO3#xxxx` creates a tag room, best of three, where `xxxx` is any valid room name.

Everything before the `#` is read as comma-separated codes, and a code that is not recognised is ignored. What a
player types is the room key itself: the room is created on the first join, and everyone who joins must type the
same string. A `$` after the `#` separates the name from a password — the portal flags such a room as password
protected, and room lists served to anonymous viewers hide what follows the `$`.

## Configuration

Configuration entries are merged from three sources, in increasing priority:

1. **Every file in the configuration directory** — `SRVPRO_CONFIG_PATH`, default `srvpro/config` in the source
   tree. `json`, `yml`, `yaml`, `toml`, `conf` and `ini` are read, and each entry is named `<file>_<key>`, so a
   `server.toml` holding `port = 7911` becomes `server_port`.
2. **Every `SRVPRO_*` environment variable**, lowercased.
3. **The `config` table of the database**, which is what the portal writes to.

See [`variables.md`](variables.md) for the full list of variables.

## HTTP API

Compatible with the original srvpro, so the original dashboard still works. We recommend using the UI for
configuration.

## Crates

| Crate | Role |
| ----- | ---- |
| `srvpro` | the core server: players, rooms, plugins, game modes and the protocol plumbing |
| `srvpro-api` | the HTTP API: JWT authentication, the account database, the plugin and configuration endpoints, and hosting the portal |
| `srvpro-app` | the binary; wires the API in and runs the server |
| `srvpro-portal` | the portal itself — Preact, Ant Design and Vite |
